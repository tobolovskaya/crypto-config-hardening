# Аналіз криптографічних конфігурацій

## crypto_config_we.yaml - Критичні помилки

### Помилка 1: JWT algorithm: none
**Проблема:** Використання алгоритму `none` означає, що токен взагалі не підписується і не захищений.

**Чому це небезпечно:** 
- Атакуючий може створити будь-який JWT токен без перевірки автентичності
- Повна відсутність захисту від підробки токенів
- Порушується основний принцип JWT - підтвердження автентичності

**Виправлення:** Використовувати сучасні алгоритми:
- `HS256` (HMAC з SHA-256) для симетричного шифрування
- `RS256` або `ES256` для асиметричного шифрування

### Помилка 2: verify_signature: false
**Проблема:** Вимкнена перевірка підпису JWT токену.

**Чому це небезпечно:**
- Навіть якщо токен підписаний, підпис не перевіряється
- Атакуючий може модифікувати payload токену без виявлення
- Повна компрометація системи автентифікації

**Виправлення:** Завжди встановлювати `verify_signature: true`

### Помилка 3: hash_function: sha1
**Проблема:** SHA-1 є застарілим і криптографічно зламаним алгоритмом хешування.

**Чому це небезпечно:**
- SHA-1 вразливий до колізій (можна знайти два різні паролі з однаковим хешем)
- Існують ефективні атаки на SHA-1
- Швидкість хешування дозволяє brute-force атаки
- SHA-1 не використовує сіль (salt)

**Виправлення:** Використовувати спеціалізовані функції для паролів:
- `bcrypt` (рекомендовано, з cost factor 12+)
- `argon2` (найсучасніший, переможець Password Hashing Competition 2015)
- `scrypt`

### Помилка 4: iv_strategy: fixed_iv
**Проблема:** Використання фіксованого вектору ініціалізації (IV) для AES-CBC.

**Чому це небезпечно:**
- Однакові дані будуть шифруватися в однакові шифротексти
- Атакуючий може виявити повторювані патерни
- Порушується семантична безпека шифрування
- Можливі атаки на відновлення ключа

**Виправлення:** Генерувати новий випадковий IV для кожної операції шифрування

### Помилка 5: exp_required: false
**Проблема:** Не вимагається поле expiration (термін дії) в JWT claims.

**Чому це небезпечно:**
- Токени можуть використовуватися необмежено довго
- Скомпрометовані токени залишаються дійсними назавжди
- Неможливо обмежити час життя сесії

**Виправлення:** Встановити `exp_required: true` і визначити розумний термін дії (наприклад, 15 хвилин для access tokens)

### Помилка 6: key_size: 1024 для none algorithm
**Проблема:** Розмір ключа 1024 біта є недостатнім для сучасних стандартів безпеки (хоча це не має значення при algorithm: none).

**Виправлення:** Використовувати мінімум 2048 біт для RSA, краще 3072 або 4096

## crypto_config_le.yaml - Середні помилки

### Помилка 1: shared_secret: "hardcoded-secret"
**Проблема:** Секретний ключ закодований безпосередньо в конфігураційному файлі.

**Чому це небезпечно:**
- Ключ може потрапити в систему контролю версій (Git)
- Всі, хто має доступ до коду, бачать секрет
- Неможливо змінити ключ без зміни коду
- Порушення принципу розділення коду та конфігурації

**Виправлення:** 
- Зберігати секрети в змінних оточення (environment variables)
- Використовувати секретні менеджери (AWS Secrets Manager, HashiCorp Vault, Azure Key Vault)
- Ніколи не комітити секрети в репозиторій

### Помилка 2: salt: fixed_salt
**Проблема:** Використання фіксованої солі для всіх паролів.

**Чому це небезпечно:**
- Один і той же пароль матиме однаковий хеш для різних користувачів
- Атакуючий може створити одну rainbow table для всіх паролів
- Компрометація одного пароля допомагає зламати інші
- Bcrypt повинен генерувати унікальну сіль для кожного пароля

**Виправлення:** 
- Генерувати випадкову сіль для кожного пароля окремо
- Bcrypt автоматично генерує та зберігає сіль у хеші - використовувати цю функціональність
- Видалити параметр `salt: fixed_salt`

### Помилка 3: algorithm: DES
**Проблема:** DES (Data Encryption Standard) - застарілий алгоритм з малою довжиною ключа (56 біт).

**Чому це небезпечно:**
- DES зламаний і може бути зламаний за лічені години навіть на звичайному обладнанні
- Розмір ключа 56 біт недостатній для сучасних обчислювальних потужностей
- DES офіційно виведений зі стандартів у 2005 році
- Існують відомі атаки (наприклад, differential cryptanalysis)

**Виправлення:** 
- Використовувати AES (Advanced Encryption Standard) з довжиною ключа 256 біт
- Режим роботи: AES-GCM (забезпечує як шифрування, так і автентифікацію)
- Або AES-CBC з HMAC для автентифікації

### Помилка 4: key_storage: hardcoded
**Проблема:** Ключі шифрування зберігаються безпосередньо в коді.

**Чому це небезпечно:**
- Аналогічно hardcoded-secret для JWT
- Ключі шифрування можуть потрапити до репозиторію
- Неможливо ротувати ключі без зміни коду
- Порушення вимог PCI DSS, GDPR та інших стандартів

**Виправлення:**
- Використовувати Key Management Services (KMS)
- Зберігати ключі в HSM (Hardware Security Module) для критичних систем
- Використовувати envelope encryption

## crypto_config_mi.yaml - Незначні помилки (найкраща конфігурація)

### Помилка 1: time_cost: 1, memory_cost: 1024, parallelism: 1
**Проблема:** Занадто низькі параметри для Argon2, що робить хешування надто швидким.

**Чому це небезпечно:**
- При низьких параметрах Argon2 втрачає свою основну перевагу - стійкість до brute-force
- Атакуючий може швидко перевіряти багато варіантів паролів
- Argon2 розроблений для того, щоб бути повільним і ресурсоємним

**Виправлення:** Рекомендовані параметри OWASP для Argon2id:
```yaml
hash_function: argon2id
time_cost: 2        # мінімум 2 ітерації
memory_cost: 19456  # 19 MiB (19456 KiB)
parallelism: 1      # залежить від сервера
```

### Помилка 2: iv_strategy: fixed_iv
**Проблема:** Навіть для AES-GCM використовується фіксований IV (вектор ініціалізації).

**Чому це небезпечно:**
- Для AES-GCM це критична помилка - повторне використання nonce з тим же ключем повністю компрометує безпеку
- AES-GCM з повторюваним nonce дозволяє відновити ключ шифрування
- Один з найнебезпечніших сценаріїв для authenticated encryption

**Виправлення:**
```yaml
iv_strategy: random_iv  # або crypto_random_nonce
nonce_length: 96        # 96 біт для GCM (12 байт)
```
- Генерувати новий випадковий nonce для КОЖНОГО шифрування
- Використовувати криптографічно стійкий генератор випадкових чисел (CSPRNG)

### Помилка 3: Відсутність обмежень на JWT claims
**Проблема:** Хоча алгоритм та верифікація правильні, відсутні важливі налаштування для claims.

**Чому це може бути небезпечно:**
- Немає вимоги до expiration time
- Немає перевірки audience (для кого призначений токен)
- Немає перевірки issuer (хто видав токен)

**Виправлення:** Додати:
```yaml
jwt:
  algorithm: RS256
  key_size: 2048
  verify_signature: true
  claims:
    exp_required: true
    exp_max_time: 900      # 15 хвилин для access token
    aud_check: true
    aud_value: "your-app"
    iss_check: true
    iss_value: "your-auth-server"
    nbf_check: true        # not before
```

## Загальні рекомендації

### Найкращі практики для JWT:
1. **Алгоритм:** RS256, ES256, або HS256 (якщо можна безпечно зберігати shared secret)
2. **Розмір ключа:** RSA ≥ 2048 біт, ECDSA ≥ 256 біт
3. **Обов'язкові claims:** exp, iat, iss, aud
4. **Термін дії:** Access tokens 5-15 хвилин, Refresh tokens 7-30 днів
5. **Завжди перевіряти підпис**

### Найкращі практики для паролів:
1. **Функція хешування:** Argon2id (найкраще) або bcrypt (мінімум cost 12)
2. **Унікальна сіль:** Для кожного пароля своя випадкова сіль
3. **Параметри:** Налаштовувати так, щоб хешування займало ~100-500 мс
4. **Ніколи не зберігати паролі у відкритому вигляді**

### Найкращі практики для шифрування:
1. **Алгоритм:** AES-256-GCM (authenticated encryption)
2. **IV/Nonce:** Завжди випадковий, ніколи не повторювати
3. **Довжина ключа:** 256 біт
4. **Зберігання ключів:** KMS, HSM, або як мінімум змінні оточення
5. **Ротація ключів:** Регулярна заміна ключів

### Пріоритети виправлення:

**Критичні (виправити негайно):**
- crypto_config_we.yaml - всі помилки критичні
- crypto_config_mi.yaml - fixed_iv для GCM
- crypto_config_le.yaml - DES encryption

**Високий пріоритет:**
- Hardcoded secrets та ключі
- Fixed salt для паролів

**Середній пріоритет:**
- Низькі параметри Argon2
- Відсутність JWT claims перевірок

## Висновок

Найгірша конфігурація: **crypto_config_we.yaml** - має критичні помилки, які роблять систему повністю незахищеною.

Середня конфігурація: **crypto_config_le.yaml** - використовує застарілі алгоритми та hardcoded secrets.

Найкраща конфігурація: **crypto_config_mi.yaml** - використовує сучасні алгоритми, але потребує покращення параметрів та усунення fixed_iv для GCM.
